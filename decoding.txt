A decision diamond in flowchart standards (like UML or BPMN) represents a runtime conditional gateway—implying that at that exact moment in the execution loop, the system evaluates a dynamic condition (like checking a variable or a score) to decide which path to take.

For LLM decoding, that is completely misleading for two reasons:

1. It’s a configuration, not a runtime branch: Temperature and sampling parameters are static configuration settings passed into the inference engine at request time (e.g., temperature=0.0 vs temperature=0.7), not something the code evaluates dynamically token-by-token.
2. It implies mixed execution: A diamond makes it look like the model might flip back and forth between greedy and sampling mid-generation, which doesn't happen in a standard generation run.

How to Fix the Diagram Visually

Since it's an either/or configuration mode rather than a dynamic flowchart branch, a decision diamond is the wrong visual metaphor. Instead, the diagram should use one of these patterns:

⚬ The Configuration Split / Swimlanes: Have the flow from LM Head \rightarrow Raw Logits lead into a box labeled "Decoding Configuration Profile Selected". From there, split the diagram into two distinct, parallel architectural tracks:
  ⚬ Track A: Greedy Decoding Pipeline (T = 0)
  ⚬ Track B: Sampling Decoding Pipeline (T > 0)
⚬ Explicit Side-by-Side Cards: Instead of trying to connect them with a flowchart arrow, layout the graphic as two separate, mutually exclusive processing columns under a shared input ("Raw Logits"). This instantly signals to the reader: "Your config determines which of these two independent pipelines executes."
