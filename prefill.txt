It is completely understandable why this diagram looks confusing at first glance! Because both phases use the exact same transformer layers, they look structurally identical. However, Prefill and Decode handle data and compute workloads in completely opposite ways.

1. Prefill vs. Decode: Why do they look the same, but work differently?

While both boxes show tokens passing through embedding and decoder layers to output a next token, how they process data is fundamentally different:

⚬ Prefill (Process the Prompt):
  ⚬ What it does: It takes the entire user prompt all at once and processes all of its tokens in parallel (matrix-matrix multiplication).
  ⚬ Main Job: It chews through the whole input chunk to understand context and writes the initial Key (K) and Value (V) states for every prompt token into the KV cache.
⚬ Decode (Generate Response):
  ⚬ What it does: It operates autoregressively, processing one single token at a time (e.g., generating "Ana", then taking "Ana" to generate "Rao").
  ⚬ Main Job: Instead of re-reading the whole prompt, it relies on the cache for historical context and generates new tokens sequentially.

2. Demystifying the Cache-to-Decode Arrow

The blue arrow pointing from the Per-layer KV cache back into the Decoder layers during the Decode phase says: "Read earlier K, V; append current K, V". This arrow represents a two-way traffic loop during every single generation step:

1. The Read (Looking Back): When the new token (like "Ana") enters the decoder layers, it needs to "attend" to all previous words in the conversation history. Instead of recalculating the past, the layer reads the stored K and V vectors for layers 1 \dots L out of the KV cache.
2. The Append (Saving for Next Time): The model then computes the new K and V vectors specifically for "Ana" and appends them to the end of the KV cache. That way, when the next token ("Rao") is generated, the cache is one token longer.

Summary Analogy

⚬ Prefill is like reading an entire book chapter in one quick sweep and writing down a summary index (building the KV cache).
⚬ Decode is writing the next sentence of a story one word at a time, looking back at your summary index to stay consistent, and adding your new word to the index as you go.

  ⚬ Path A (Prefill): A wide, parallel arrow feeding the whole prompt chunk in at once.
  ⚬ Path B (Decode): A looping arrow feeding single tokens back through that same block.
2. Re-anchor the KV Cache: Move the Per-layer KV Cache to a central position between or below the phases rather than off to the right side. This makes the data flow much more intuitive:
  ⚬ Prefill does a massive one-time write downward into the cache.
  ⚬ Decode acts as a loop that reads from and appends to that central memory on every tick, without the long, confusing cross-diagram arrows.

So while the logic in the current diagram is technically correct, changing the layout to highlight parallel batch vs. sequential loop would make it instantly crystal clear at a glance!
The KV cache fits directly inside the Scaled Dot-Product Attention mechanism within each Transformer decoder layer. It is not a separate network layer or external database; rather, it is a memory persistence buffer that stores the intermediate Key (K) and Value (V) tensors of all preceding tokens so they don't have to be recomputed during autoregressive generation.

To see exactly how it plugs into the attention architecture, it helps to look at what happens to the three projection vectors (Q, K, and V):

1. Where Q, K, and V Intersect with the Cache

Within every attention head of every transformer layer, input tokens are projected into three matrices:

⚬ Queries (Q): Represent the current token(s) looking for context. Never cached. In the decode phase, Q is computed only for the single new token being processed.
⚬ Keys (K): Represent the index tags of tokens that provide context.
⚬ Values (V): Represent the actual content/features associated with those tokens.

During the Decode phase, the attention operation evaluates the current token’s Q against the historical K and V vectors stored in the cache:

$$\text{Attention}(Q_{\text{current}}, K_{\text{combined}}, V_{\text{combined}}) = \text{softmax}\left(\frac{Q_{\text{current}} K_{\text{combined}}^T}{\sqrt{d_k}}\right) V_{\text{combined}}$$

Where:

⚬ K_{\text{combined}} = [\text{KV Cache } K \text{ tensors} \mathbin{\Vert} K_{\text{current}}] (historical keys concatenated with the new token's key)
⚬ V_{\text{combined}} = [\text{KV Cache } V \text{ tensors} \mathbin{\Vert} V_{\text{current}}] (historical values concatenated with the new token's value)

2. Structural Placement in the Architecture

⚬ Per-Layer Granularity: The cache is split into L separate segments (one for each transformer layer, 1 \dots L). Layer 5's attention mechanism only reads and writes to Layer 5's KV cache slice; it never touches Layer 4's cache.
⚬ Inside the Attention Block: Architecturally, it sits right between the linear projection step (where K and V are generated) and the matrix multiplication (matmul) step where attention weights are calculated.

Without the KV cache intercepting K and V at this exact spot in the attention pipeline, generating token N would require re-running the self-attention matrix multiplication across all N-1 previous tokens from scratch, driving generation complexity up to O(N^2) per step instead of O(1) compute per historical token.
